2 · How a Trigger Actually Travels

Six steps from a keypress on the master to a 9V pulse on the slave — this is the path every command follows.

  1. 01

    Type & confirm name

    Multi-tap keypad enters S-SLAVE001, OLED echoes it live, then * confirms send.

  2. 02

    Encrypt & checksum

    Payload MASTERID|NAME|TRIG|seq is padded, AES-128 encrypted, CRC16 appended.

  3. 03

    Burst across 3 channels

    4 transmit bursts hop 433.0 / 433.2 / 433.4 MHz through the amplifier + RF switch, non-blocking.

  4. 04

    Slave wakes & listens

    Every ~8s the slave wakes from deep sleep, runs Channel Activity Detection on all 3 frequencies.

  5. 05

    Decrypt, verify, match

    Packet is decrypted, CRC checked, sequence number checked against last-seen (blocks replay), name compared to its own.

  6. 06

    Fire output + beep

    MOSFET switches 9V/1A for 2s to the relay/light; master gets single beep + "Triggered" on success.

3 · Flaws Found in the Original Design

Reviewed against the source manual. Each item below was corrected in the diagram above and should be applied to the real build.

Pin conflict: status LED shares A1 with the keypad
ledPin = A1 is also keypad column pin 4 (colPins[3] = 15). The Keypad library repeatedly changes that pin's mode while scanning — driving it as an LED output during every transmit will corrupt key reads. Every other digital pin on the Nano is already spoken for by this design (SPI bus, keypad, OLED, SD, buzzer, TX-enable), so there's no free GPIO to move it to.

Fix applied: the dedicated LED pin is removed entirely — the status LED is instead wired (with a series resistor) directly off the existing A3 TX-enable line, since both signals mean exactly the same thing: "radio is transmitting."
No replay protection on commands
AES-128 + CRC16 only prove the message wasn't tampered with — not that it's fresh. Anyone who captures one TRIG packet over the air can re-broadcast it later and fire the slave's output, without ever knowing the key.

Fix applied: a monotonically increasing sequence number is added to the payload before encryption; the slave stores the last-seen value in EEPROM and silently drops anything at or below it.
Slave battery undersized for the 9V/1A pulse
A 500mAh protected Li-ion feeds a boost converter delivering 9V @1A. Accounting for boost efficiency, that's roughly 2.4–2.7A pulled from the 3.7V cell for every 2-second trigger — enough to sag the rail or trip the protection IC. The manual's own troubleshooting table names this symptom ("battery sag on trigger") without changing the BOM.

Fix applied: spec bumped to a 1500mAh cell with a PCM rated for >3A continuous discharge.
General-purpose relay used for RF antenna switching
The SPDT relay in the BOM is a generic 5V signal relay, not 50Ω impedance-matched. Using it to switch the antenna between the amplifier (TX) and the LoRa module (RX) at 433MHz introduces mismatch and insertion loss — directly working against the >5km range the guide promises.

Fix applied: swapped for an RF-rated T/R switch (or a dedicated PA with built-in TX/RX switching) in the diagram.
Master doesn't verify the ACK's integrity
The slave's incoming commands are CRC-checked, but the master accepts a rename ACK from the slave on a simple startsWith() match, with no CRC verification on that inbound packet. Low severity, but inconsistent with the rest of the security model.

Recommendation: reuse the same CRC-append/verify routine symmetrically on ACK packets.
